Issue 1: Build the core Argument Board model

## What to build

Build the domain model for a single active Argument Board. The model should represent one Question and one Answer, the SCQA frame, Supporting Arguments under the Answer, Supporting Data or Facts under a specific Supporting Argument, Support Mode, optional Data Type, Evidence Links, touched/empty-slot state, ordering, schema version, and board metadata.

The model should create the default board with empty slots: one SCQA frame, three Supporting Argument slots, and three Supporting Data or Facts slots under each Supporting Argument. Empty untouched slots should not count as incomplete.

## Acceptance criteria

- [ ] A new Argument Board contains empty Situation, Complication, Question, and Answer fields.
- [ ] A new Argument Board contains exactly one Question and one Answer.
- [ ] A new Argument Board starts with three empty Supporting Argument slots.
- [ ] Each default Supporting Argument starts with three empty Supporting Data or Facts slots.
- [ ] Supporting Data or Facts attach to a specific Supporting Argument, not directly to the Answer.
- [ ] Supporting Argument supports two Support Mode values: Reasoning / Interpretation and Evidence-backed.
- [ ] Supporting Data or Facts supports optional Data Type values: Fact, Observation, Example, and Estimate.
- [ ] Empty untouched slots do not create readiness warnings.
- [ ] The model stores touched/incomplete state separately from empty default structure.
- [ ] Unit tests cover default board creation, hierarchy constraints, support mode, optional data type, touched state, and one-answer rules.

## Blocked by

None - can start immediately.


Issue 2: Render the default structured board with inline editing

## What to build

Render the primary board surface for editing the Argument Board. The first screen should be the usable board, not a landing page. Users should edit content inline, using plain-language primary labels with formal framework terms as small secondary labels or tooltips.

The board should feel canvas-like while remaining structurally constrained. Users should be able to click into empty slots and type directly.

## Acceptance criteria

- [ ] The app opens directly to the usable Argument Board.
- [ ] SCQA fields render with plain-language labels: What is happening?, What changed or makes this matter?, What question must this answer?, What is your main answer?
- [ ] Supporting Argument fields render with the plain-language label: Why should someone believe this?
- [ ] Supporting Data or Facts fields render with the plain-language label: What fact supports this?
- [ ] Evidence Link fields render with the plain-language label: Where can this be checked?
- [ ] Formal terms appear only as secondary labels or tooltips.
- [ ] Users can edit SCQA, Supporting Arguments, Supporting Data or Facts, and Evidence Links inline.
- [ ] Empty default slots are visually available without warning noise.
- [ ] The board remains keyboard reachable.
- [ ] Browser tests cover first-load board rendering and inline SCQA editing.

## Blocked by

- Issue 1: Build the core Argument Board model.


Issue 3: Add support editing controls for add, reorder, duplicate, delete, and support modes

## What to build

Add the editing controls that make the board usable for real argument construction. Users should be able to add as many Supporting Arguments and Supporting Data or Facts as they need, reorder Supporting Arguments, reorder Supporting Data or Facts within their own Supporting Argument, duplicate whole Supporting Argument branches, duplicate individual Supporting Data or Facts, delete items, and set Support Mode through a segmented control.

Dragging may be added as an enhancement, but keyboard-accessible move controls are required. Dragging must reorder only within the structured hierarchy and must not create free-position nodes.

## Acceptance criteria

- [ ] Users can add more Supporting Arguments beyond the default three.
- [ ] Users can add more Supporting Data or Facts under a Supporting Argument beyond the default three.
- [ ] Users can reorder Supporting Arguments.
- [ ] Users can reorder Supporting Data or Facts within their own Supporting Argument.
- [ ] Moving Supporting Data or Facts between different Supporting Arguments is not exposed in version 1.
- [ ] Users can delete Supporting Arguments and Supporting Data or Facts.
- [ ] Users can duplicate a Supporting Argument branch, including text, Support Mode, Supporting Data or Facts, Evidence Links, and touched/incomplete states.
- [ ] Users can duplicate individual Supporting Data or Facts.
- [ ] Support Mode is edited through a segmented control on each Supporting Argument.
- [ ] Undo and redo work for add, edit, delete, reorder, duplicate, and support-mode changes.
- [ ] Browser tests cover add, delete, duplicate, reorder, support-mode controls, and undo/redo.

## Blocked by

- Issue 1: Build the core Argument Board model.
- Issue 2: Render the default structured board with inline editing.


Issue 4: Add readiness review for argument structure and evidence links

## What to build

Add the review checklist engine and UI. The checklist should evaluate logic readiness and structure only. It must not judge truth, proof, persuasiveness, writing quality, or assign numeric scores.

The checklist should flag missing required content, evidence-backed Supporting Arguments without data/facts, Supporting Data or Facts with missing or invalid Evidence Links, touched empty fields, and generation failures for Preview or Export File.

## Acceptance criteria

- [ ] Checklist flags missing Situation, Complication, Question, and Answer.
- [ ] Checklist flags an Answer with no Supporting Argument.
- [ ] Checklist flags Evidence-backed Supporting Arguments that have no Supporting Data or Facts.
- [ ] Checklist does not require Supporting Data or Facts for Reasoning / Interpretation Supporting Arguments.
- [ ] Checklist flags Supporting Data or Facts with text but no Evidence Link.
- [ ] Checklist flags invalid Evidence Link format.
- [ ] URL validation accepts http:// and https:// only.
- [ ] URL validation does not fetch URLs, check whether pages exist, score source quality, or verify source support.
- [ ] Empty untouched default slots do not create warnings.
- [ ] Touched empty items are flagged.
- [ ] The UI avoids claims that the argument is correct, proven, persuasive, or scored.
- [ ] Unit tests cover all checklist outcomes and URL-format boundaries.

## Blocked by

- Issue 1: Build the core Argument Board model.
- Issue 2: Render the default structured board with inline editing.
- Issue 3: Add support editing controls for add, reorder, duplicate, delete, and support modes.


Issue 5: Add local Export File download and upload replacement flow

## What to build

Add explicit local file persistence. Users can download the current Argument Board as a human-inspectable `.argument.json` Export File and upload a previous Export File to replace the current board. The app should not autosave in browser storage and should not store hidden telemetry or unnecessary personal data in the file.

Upload replaces the active board. Merge import, board libraries, and multiple open boards are out of scope.

## Acceptance criteria

- [ ] Users can download the active board as a `.argument.json` file.
- [ ] Export File includes schema version, app name, created timestamp, updated timestamp, board title, SCQA content, Supporting Arguments, Support Modes, Supporting Data or Facts, Evidence Links, touched/empty-slot state, and optional layout preferences.
- [ ] Export File excludes device information, user identity, browsing history, analytics IDs, hidden telemetry, and unnecessary personal data.
- [ ] Users can upload a valid Export File to restore a board.
- [ ] Upload replaces the current board rather than merging.
- [ ] Upload asks for confirmation when the current board contains touched content.
- [ ] Invalid JSON and unsupported schema versions show clear messages.
- [ ] Unknown future fields are preserved when reasonable.
- [ ] Reopening the app starts clean unless the user imports an Export File.
- [ ] Tests cover export shape, privacy exclusions, round-trip fidelity, invalid import, unsupported schema, and replacement confirmation.

## Blocked by

- Issue 1: Build the core Argument Board model.
- Issue 2: Render the default structured board with inline editing.
- Issue 4: Add readiness review for argument structure and evidence links.


Issue 6: Add Clear Board and unsaved-content protection

## What to build

Add Clear Board behavior and unsaved-content protection. Clear Board should reset the active board to the default empty slots. If the board has no touched content, it should clear immediately. If the board has touched content, it should ask for confirmation and remind the user to download first if they want to keep the board.

Refreshing or closing with unsaved content should warn the user when technically possible. Clear Board should never affect previously downloaded local Export Files.

## Acceptance criteria

- [ ] Clear Board resets to the default empty board.
- [ ] Clear Board runs immediately when there is no touched content.
- [ ] Clear Board asks for confirmation when touched content exists.
- [ ] Confirmation reminds users to download first if they want to keep the board.
- [ ] Clear Board does not affect downloaded local Export Files.
- [ ] Refreshing or closing with unsaved content warns the user when technically possible.
- [ ] Browser tests cover untouched clear, touched clear confirmation, and refresh/close warning behavior where testable.

## Blocked by

- Issue 1: Build the core Argument Board model.
- Issue 2: Render the default structured board with inline editing.
- Issue 5: Add local Export File download and upload replacement flow.


Issue 7: Add Copy Outline for drafting handoff

## What to build

Add Copy Outline so users can move from argument planning into drafting elsewhere. Version 1 should stop at argument structure plus copied outline; it should not include a full prose editor, DOCX export, PDF export, or rich formatted document export.

The copied outline should preserve the SCQA and Minto hierarchy and include readiness markers for incomplete evidence.

## Acceptance criteria

- [ ] Users can copy an outline from the current board.
- [ ] Copied outline includes title, Situation, Complication, Question, and Answer.
- [ ] Copied outline includes Supporting Arguments in board order.
- [ ] Copied outline includes Support Mode for each Supporting Argument.
- [ ] Copied outline includes Supporting Data or Facts under the correct Supporting Argument.
- [ ] Copied outline includes Evidence Links.
- [ ] Copied outline includes Data Type only when selected.
- [ ] Copied outline includes an Incomplete Evidence section when relevant.
- [ ] Copy Outline works without adding a full prose editor.
- [ ] Tests cover hierarchy, ordering, support modes, data types, evidence links, and incomplete evidence markers.

## Blocked by

- Issue 1: Build the core Argument Board model.
- Issue 2: Render the default structured board with inline editing.
- Issue 3: Add support editing controls for add, reorder, duplicate, delete, and support modes.
- Issue 4: Add readiness review for argument structure and evidence links.


Issue 8: Add Mermaid-compatible Argument Preview mode

## What to build

Add a separate Preview mode or tab that visualizes the Argument Board as a read-only graph or workflow. The Preview generator should produce Mermaid-compatible flowchart text from the board model. The app should render the graph visually when practical, provide Copy Mermaid, and show Mermaid text plus a clear error if rendering fails.

Preview is for inspection, not editing. It should include readiness markers and omit empty untouched slots.

## Acceptance criteria

- [ ] Users can switch from Board mode to Preview mode or tab.
- [ ] Preview is read-only and does not become the editing surface.
- [ ] Preview generator produces Mermaid-compatible flowchart text.
- [ ] Preview graph includes SCQA, Supporting Arguments, Supporting Data or Facts, and Evidence Links where present.
- [ ] Evidence-backed Supporting Arguments with no Supporting Data or Facts show a needs-data marker.
- [ ] Supporting Data or Facts with no Evidence Link show a needs-evidence-link marker.
- [ ] Supporting Data or Facts with invalid Evidence Links show an invalid-evidence-link marker.
- [ ] Empty untouched slots are omitted from Mermaid output.
- [ ] Empty touched slots appear with an empty marker.
- [ ] Users can Copy Mermaid.
- [ ] Render failures show Mermaid text and a clear rendering error.
- [ ] Tests cover Mermaid output, readiness markers, Copy Mermaid, read-only behavior, and render-failure fallback.

## Blocked by

- Issue 1: Build the core Argument Board model.
- Issue 2: Render the default structured board with inline editing.
- Issue 3: Add support editing controls for add, reorder, duplicate, delete, and support modes.
- Issue 4: Add readiness review for argument structure and evidence links.


Issue 9: Apply Olive Garden Feast visual system and responsive layout

## What to build

Apply the visual system and responsive layout to the complete board, controls, checklist, outline actions, and Preview mode. The app should be compact but calm, closer to an expert worksheet than a spacious landing page. It should be optimized for desktop/tablet while remaining usable on mobile.

Use the Olive Garden Feast palette with restrained status colors and accessible contrast.

## Acceptance criteria

- [ ] The first screen remains the usable board with no decorative hero or marketing section.
- [ ] The board uses #FEFAE0 for background and #283618 for primary text.
- [ ] Primary actions use #606C38.
- [ ] Warning or incomplete states use #DDA15E.
- [ ] Destructive or attention states use #BC6C25.
- [ ] SCQA appears as four compact panels on desktop/tablet where space allows.
- [ ] Answer visually anchors the support section.
- [ ] Supporting Arguments appear as stacked lanes or compact cards below Answer.
- [ ] Supporting Data or Facts appear as smaller rows inside each Supporting Argument.
- [ ] Mobile stacks SCQA vertically and keeps Supporting Arguments vertically stacked.
- [ ] Preview can scroll on mobile.
- [ ] Controls remain touch reachable and keyboard reachable.
- [ ] Accessibility checks cover focus visibility, semantic labels, keyboard reachability, color contrast, and no text overlap.
- [ ] Responsive checks cover desktop, tablet, and mobile widths.

## Blocked by

- Issue 3: Add support editing controls for add, reorder, duplicate, delete, and support modes.
- Issue 8: Add Mermaid-compatible Argument Preview mode.


Issue 10: Complete end-to-end verification suite

## What to build

Complete the verification suite around the final version 1 behavior. Domain tests should remain the first priority, followed by browser-level coverage for the core user flow. This issue should harden regressions across model behavior, editing, readiness review, import/export, clearing, outline copy, Preview, visual layout, responsiveness, and accessibility.

## Acceptance criteria

- [ ] Domain tests cover Argument Board creation, one-answer rule, hierarchy constraints, Support Mode, Data Type, touched state, and default slots.
- [ ] Reducer tests cover add, edit, delete, reorder, duplicate, undo, redo, reset, import, and replacement confirmation behavior.
- [ ] Import/export tests cover `.argument.json`, schema version, privacy exclusions, round-trip fidelity, invalid files, unsupported schema versions, and reasonable future-field preservation.
- [ ] Review tests cover missing SCQA, unsupported Answer, Evidence-backed support gaps, missing Evidence Links, invalid Evidence Links, untouched empty slots, and touched empty slots.
- [ ] Outline tests cover ordering, hierarchy, title, Support Modes, Data Types, Evidence Links, and incomplete evidence markers.
- [ ] Preview tests cover Mermaid output, readiness markers, Copy Mermaid, read-only behavior, and render-failure fallback.
- [ ] Browser tests cover first load, inline editing, adding/reordering/duplicating/deleting support, Support Mode changes, evidence-link states, Copy Outline, Preview mode, Copy Mermaid, download/upload round trip, Clear Board confirmation, and responsive sanity checks.
- [ ] Accessibility checks pass for keyboard reachability, focus visibility, semantic labels, and contrast.
- [ ] Layout checks pass for no text overlap and no cramped controls at common desktop, tablet, and mobile widths.
